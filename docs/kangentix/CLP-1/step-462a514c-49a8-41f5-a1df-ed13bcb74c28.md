# Implementation Plan – Dark / Light Theme Manual Switch

---

## 1. Overview & Scope

**Goal** – Give users a control in the Settings panel to select the UI appearance (light, dark, or follow the OS). The chosen appearance must be applied instantly and persisted across restarts.

**Included**
- UI control (select‑dropdown) in Settings.
- New `theme` entry in the persisted settings store.
- Runtime theme‑switching logic that updates CSS variables immediately.
- Persistence through the existing `electron-store` mechanism.
- Tests covering defaults, validation, and persistence.

**Excluded**
- Additional themes (high‑contrast, custom colors).
- Localization of the new UI text.
- Modifications to the tray icon beyond the existing system template.

| Area | Files to Change | Reason |

## 3. Detailed Changes

### 3.1 Shared Types (`shared/types.d.ts`)
```ts
export interface Settings {
  monitoring: boolean;
  shortcut: string;
  maxItems: number;
  launchAtLogin: boolean;
  /**
   * UI appearance. `system` follows the OS colour‑scheme, `light` forces the light theme, and `dark` forces dark.
   */
  theme: 'system' | 'light' | 'dark';
}
```
*Why*: Centralises the contract; TypeScript will enforce correct usage in both processes.

### 3.2 Main‑Process Settings (`electron/settings.ts`)
1. **Defaults** – add `theme: 'system'` to the `defaults` object.
2. **Parser** – add a case in `parseSetting`:
```ts
case 'theme':
  if (value === 'system' || value === 'light' || value === 'dark') {
    return { theme: value };
  }
  break;
```
3. No other code changes are required; `applySettings` already saves the patch and broadcasts `settings:changed`.

*Error handling*: Invalid values throw as before; the renderer will revert the UI to the stored value.

### 3.3 Renderer UI (`renderer/index.html`)
Add a new control under an **Appearance** subsection (or within *General*). Example markup:
```html
<div class="settings-section">
  <h3>Appearance</h3>
  <label class="setting-row">
    <span>Theme</span>
    <select id="setting-theme">
      <option value="system">Follow system</option>
      <option value="light">Light</option>
      <option value="dark">Dark</option>
    </select>
  </label>
</div>
```
*Accessibility*: The `<select>` is natively keyboard‑focusable and announces its label via the surrounding `<label>`.

### 3.4 Renderer Logic (`renderer/renderer.ts`)
1. **Extend UI map**:
```ts
theme: element<HTMLSelectElement>('setting-theme'),
```
2. **Update `renderSettings`** to set the control value and apply the theme:
```ts
ui.theme.value = settings.theme;
applyTheme(settings.theme);
```
3. **Add `applyTheme` helper** (run on start and on every settings change):
```ts
function applyTheme(theme: Settings['theme']) {
  const root = document.documentElement; // <html>
  if (theme === 'system') {
    root.removeAttribute('data-theme');
  } else {
    root.setAttribute('data-theme', theme);
  }
}
```
4. **Persist changes** – attach a `change` listener:
```ts
ui.theme.addEventListener('change', () =>
  void saveSetting('theme', ui.theme.value as Settings['theme'])
);
```
5. **Hook into existing callbacks** – the existing `api.onSettingsChanged(renderSettings)` will now also re‑apply the theme when another process (e.g., a remote UI) updates the setting.

### 3.5 CSS Overrides (`renderer/style.css`)
After the existing `@media (prefers-color-scheme: dark) { … }` block, add explicit overrides that win over the media query when a forced theme is active:
```css
/* Forced dark theme – overrides system preference */
[data-theme="dark"] {
  --bg-primary: #1e1e1e;
  --bg-secondary: #252526;
  --bg-tertiary: #2d2d2d;
  --bg-hover: #333333;
  --bg-selected: #2d5aa0;
  --bg-selected-border: #5a9eff;
  --bg-pinned: #3d361f;
  --bg-pinned-hover: #4a4020;

  --text-primary: #e0e0e0;
  --text-secondary: #a0a0a0;
  --text-tertiary: #707070;
  --text-inverse: #1e1e1e;
  --text-link: #8ab4f8;

  --border-color: #3c3c3c;
  --border-focus: #5a9eff;

  --accent-primary: #5a9eff;
  --accent-primary-hover: #7ab6ff;
  --accent-danger: #f28b82;
  --accent-danger-hover: #ffa7a0;
  --accent-warning: #fdd663;
  --accent-success: #81c995;
}

/* Optional explicit light overrides – mostly a safety net */
[data-theme="light"] {
  /* No overrides needed; the default :root values already represent the light theme. */
}
```
_Why this approach_ – Adding a `data-theme` attribute is simple, does not require rebuilding the CSS, and works instantly because the variables are re‑evaluated on attribute change.

### 3.6 Persistence & Migration
- Existing installations will have a settings file without the `theme` key. The defaults defined in `electron/settings.ts` (`theme: 'system'`) will be used automatically.
- No migration script is required; the first load after upgrade will simply pick the default.

## 4. Data Flow & State Handling
1. **App start** – Main process creates `settings` store (with default `theme: 'system'`).
2. Renderer invokes `api.getSettings()` → receives the full `Settings` object.
3. `renderSettings` populates UI controls (including the new theme selector) and calls `applyTheme`.
4. **User changes theme** → UI `change` event triggers `saveSetting('theme', newValue)`.
5. Preload script forwards the call to `ipcMain.handle('settings:set')` → `applySettings` in `electron/main.ts` validates and writes the new value.
6. Main process emits `settings:changed` with the updated store.
7. Renderer receives the broadcast via `api.onSettingsChanged` → `renderSettings` runs again, updating the selector value and re‑applying the theme.
8. The UI updates instantly because the CSS variables are re‑evaluated when `document.documentElement` gets/loses the `data-theme` attribute.

## 5. Edge Cases & Failure Behaviour
| Situation | Expected Behaviour |
|---|---|
| **Invalid value from UI** (e.g., corrupted `<select>` due to a bug) | `parseSetting` throws; the renderer’s `saveSetting` catch block shows an error toast and re‑loads the stored value to restore UI consistency. |
| **Settings file cannot be written** (disk full) | The `saveSetting` promise rejects; UI shows an error toast and the control reverts to the last known good value. |
| **User manually edits the JSON store** and writes an unsupported value | On the next load `parseSetting` will reject that value; the main process will keep the previous valid store, and the renderer will see the persisted (valid) value. |
| **System theme changes while `theme` is set to `system`** | No attribute is set on `<html>`, so the CSS `@media (prefers-color-scheme: …)` automatically switches the UI. |
| **System theme changes while `theme` is forced (`light`/`dark`)** | The forced `[data‑theme]` attribute overrides the media query, so UI stays on the user‑chosen mode. |

## 7. Test Plan

### 7.1 Unit Tests (added to `test/suite.cjs`)
```ts
// Verify defaults now include the theme key
test('settings defaults include theme', () => {
  assert.deepEqual({ ...settings.store }, {
    monitoring: true,
    shortcut: 'CommandOrControl+Shift+V',
    maxItems: 1000,
    launchAtLogin: true,
    theme: 'system',
  });
});

// Validation of the new setting
test('valid theme settings are accepted', () => {
  for (const v of ['system', 'light', 'dark'] as const) {
    assert.deepEqual(parseSetting('theme', v), { theme: v });
  }
});

// Invalid values should be rejected
test('invalid theme settings are rejected', () => {
  const bad = ['', 'bright', true, 42, null, undefined];
  for (const v of bad) {
    assert.throws(() => parseSetting('theme', v as any), /Invalid setting/);
  }
});

// Persistence test – write then read back
test('theme persists across runs', () => {
  // Simulate a user picking dark mode
  settings.set('theme', 'dark');
  // Re‑instantiate the store to emulate a fresh app start
  const { Store } = require('electron-store');
  const fresh = new Store({ defaults: {}, name: settings.name, cwd: settings.path.replace(/clipboard\.json$/, '') });
  assert.equal(fresh.get('theme'), 'dark');
});
```
*Note*: The test suite already creates an isolated `userData` directory, so persisting to that location is safe.

## 9. Trade‑offs & Risks
- **CSS duplication** – Adding a full set of dark‑mode variable definitions for `[data-theme="dark"]` repeats the existing block. The risk is that future design‑token changes need to be mirrored in two places. Mitigation: keep the duplicated block near each other and document the need to sync them.
- **Three‑state vs binary UI** – A dropdown gives explicit control (`system`, `light`, `dark`). If the product later decides a simple binary switch is preferred, the UI can be simplified without breaking the underlying setting (the `system` value would be treated as the default). The implementation therefore adopts the more flexible three‑state design now.
- **User data migration** – Existing users will get a default `theme: 'system'`. No migration is required, but if a later version chooses a binary boolean approach, a migration layer would be needed.
- **Accessibility impact** – Using a native `<select>` ensures built‑in keyboard support and screen‑reader labeling, minimizing additional ARIA work.

## 10. Open Questions (required before finalising implementation)
1. **Toggle Behaviour** – Should the UI be a **binary** ‘Dark mode’ switch (on/off) *or* a **three‑state** selector (`System`, `Light`, `Dark`)?** The current plan assumes a three‑state selector to satisfy the “follow system when never changed” acceptance criterion.
2. **Label Text** – Preferred wording for the control? Options include:
   - "Theme"
   - "Appearance"
   - "Dark mode"
   - "Use dark theme"
   - "Appearance: System / Light / Dark"
3. **Persistence Location** – Is storing the value in `electron-store` (the same store used for other preferences) sufficient, or do we need to expose it in any external configuration file (e.g., a user‑visible JSON)?
4. **Default Behaviour Clarification** – If the user never touches the control, should the app *always* follow the OS (i.e., default `'system'`), or should we default to *light* unless the OS is dark? The ticket’s acceptance criteria point to the former, but confirmation would avoid ambiguity.
